# Experimental Tor Mode — 0.2.0

**Встроенный Tor реализован и проверен на Windows x64, режим остаётся экспериментальным.** RainCode запускает настоящий отдельный C Tor daemon из подписанного официального Expert Bundle. Устанавливать Tor Browser для этого не требуется.

Реальный сетевой smoke достиг bootstrap 100%, опубликовал собственный временный v3 onion-сервис и загрузил его внутри RainCode WebContents. В основном документе и cross-origin iframe проверены `RTCPeerConnection`, `process` и `window.raincode`: все отсутствовали. Запрос новой цепочки выполнен, New Identity заменил профиль, остановка daemon подтверждена. Артефакты: `artifacts/tor-network-smoke.json` и `artifacts/tor-owned-onion.png`. Временный адрес не публикуется и не является постоянной закладкой.

Эти проверки не означают независимую аттестацию отсутствия DNS/IP-утечек, унификацию fingerprint или поддержку Tor на всех ОС. Полные результаты: [TEST_REPORT.md](docs/release-validation.md).

> Экспериментальный Tor Mode направляет соединение через сеть Tor, но RainCode Browser не обеспечивает тот же уровень защиты от fingerprinting, что официальный Tor Browser. Для задач, где критична анонимность, используйте официальный Tor Browser.

## Использование

Откройте `raincode://tor` и явно нажмите запуск либо введите корректный v3 onion-адрес. При вводе onion из Direct/Proxy показывается отдельный запрос подтверждения; отмена не запускает daemon. После bootstrap создаётся отдельная Tor-вкладка, исходный профиль не меняется. Ввод адреса не отправляется в обычный поиск, Direct DNS или Tor2web.

На внутренней странице показаны состояние, bootstrap и диагностика. До готовности или при ошибке соединение Tor-профиля блокируется без Direct fallback. В текущем выпуске камера, микрофон, геолокация и остальные запрашиваемые разрешения в Tor запрещены политикой.

- **Новая цепочка** отправляет `SIGNAL NEWNYM`, закрывает существующие session-соединения и перезагружает Tor-страницы. Tor может ограничивать частоту; смена exit IP не гарантируется.
- **Новая личность** отправляет NEWNYM, закрывает Tor-вкладки, очищает их session и создаёт новый непостоянный профиль. Это не обещание смены browser fingerprint или удаления всех следов ОС.
- **Остановить** закрывает Tor-профили/соединения и завершает процесс.
- **Удалить временные данные** дополнительно удаляет каталоги daemon текущего запуска. При штатном выходе вызывается очистка; после аварийного выключения следы ОС/старые runtime-каталоги могут остаться.

## Сетевая изоляция

Tor-профиль использует отдельную непостоянную Electron session; его tabs/history/recently-closed/metadata загрузок исключены из сохраняемой сессии. SOCKS5 слушает loopback, без Direct/PAC/bypass. Правило `<-loopback>` отменяет неявный Chromium bypass. Локальные адреса дополнительно блокируются политикой запросов Tor.

Daemon запускается через `spawn` с фиксированным executable, массивом аргументов и `shell: false`. Control-port слушает loopback и использует cookie authentication; cookie не выдаётся сайтам и не записывается в обычные логи. Здесь используется `AUTHENTICATE` с локальным cookie, а не заявленная реализация SAFECOOKIE challenge.

Chromium получает hostname через SOCKS5. Глобальные resolver rules блокируют обычное разрешение `.onion`; dns-prefetch и QUIC отключены. До готовности daemon сетевой gate запрещает Tor-запросы. Остановка не переключает профиль на Direct.

Дополнительно используется `disable_non_proxied_udp` и минимальный Tor-only all-frame preload: он удаляет WebRTC/WebTransport constructors, не публикуя Electron/Node API. Для выполнения этого preload в subframes только у Tor включён `nodeIntegrationInSubFrames`, при сохранённых `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`. Контролируемый E2E проверяет основной документ, cross-origin и srcdoc фреймы без Node/IPC/WebRTC. Название флага не должно скрывать его риск: поведение надо перепроверять при обновлениях Electron, а не считать постоянной гарантией.

## Что проверено и что осталось

Контролируемый SOCKS5 E2E проверил production session policy: передаются доменные имена (SOCKS ATYP=3), storage разделено с Direct, WebRTC отсутствует в проверенных фреймах, закрытие SOCKS не вызывает прямой fallback. Это тест транспорта на локальном fixture, отдельно от успешного реального Tor smoke с собственным v3 service.

Ещё требуются захват DNS/UDP/IP-пакетов и долговременная проверка redirects, workers, downloads, WebSocket, WebTransport, crash/kill daemon и фонового поведения Chromium на каждой платформе. API guard не является сетевым firewall. Сам daemon закономерно подключается к сети Tor; измерять надо нежелательные прямые соединения браузера и утечки целевых имён, а не запрещать daemon доступ к relays.

Tor переносит сетевые потоки и не делает RainCode официальным Tor Browser. Аккаунты, fingerprint, расширения, локальное malware и глобальное наблюдение остаются рисками. RainCode не связан с The Tor Project и не спонсируется им.

# Диагностика адреса (0.3.1)

## Поиск и навигация0.4.0

В Tor-профиле поисковые запросы используют отдельный `torSearchTemplate`, редактируемый в Настройках. По умолчанию это лёгкий [DDG HTML](https://duckduckgo.com/duckduckgo-help-pages/features/non-javascript) через HTTPS; можно выбрать другой HTTPS или действительный onion v3 HTTP шаблон с одним `{query}`. Поисковые запросы и клирнет-ссылки проходят через ту же Tor session/SOCKS; профиль не переключается на Direct. Из Direct переход на полноценную onion-ссылку/новое окно требует native согласия и создаёт отдельную Tor-вкладку. Onion subresources в Direct блокируются без DNS и не запускают Tor.

RainCode не создаёт имена/алиасы вроде facebook.onion. Поисковик не является каталогом всех hidden services; Hidden Wiki не имеет единственного гарантированного адреса. Нужен действительный полный адрес от оператора, доступный сервис и рабочая сеть Tor. CAPTCHA, блокировка Tor exit, исчезнувший сервис и TLS ошибки не обходятся ослаблением Chromium. Для исходного404/410/empty-result ответа есть кнопка просмотра оригинала.

IP/ASN диагностика onion и Tor/Proxy hostname не делает обычных DNS-запросов; сетевой адрес onion origin скрыт протоколом. Console запускает локальные инструменты с правами пользователя по явному подтверждению: такие команды сами не получают Tor-туннель автоматически.

`facebook.onion` не является действительным onion v3 адресом и не преобразуется в скрытый alias. Нужен полный адрес оператора: 56 base32 символов перед `.onion`, версия3 и правильная контрольная сумма; v2 больше не поддерживается. RainCode проверяет формат до предложения Tor и показывает ONION_INVALID, не отправляя ошибочный адрес в DNS или поиск. Полный адрес берите с официального HTTPS-сайта владельца сервиса; доступность произвольного сервиса не гарантируется. Подробнее: [Tor Project](https://support.torproject.org/tor-browser/features/onion-services/).

HTTPS-only сохраняет HTTP onion v3 в Tor: этот транспорт уже шифруется end-to-end протоколом onion service. Для обычных сайтов через Tor требуется HTTPS; не делаем перехода на Direct при ошибке.

## Исправление холодного подключения — 0.5.2

Chromium ограничивает SOCKS handshake 30 секундами ([код Chromium](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/socket/socks_connect_job.cc)). Создание цепочки и получение дескриптора onion могут занимать больше. Для допустимых onion HTTP/HTTPS/WS/WSS запросов RainCode сначала открывает TCP-stream через уже готовый локальный Tor SOCKS5 (ATYP03), не отправляя HTTP-запрос или тело, затем закрывает этот stream и разрешает обычную Chromium-загрузку через тот же Tor daemon. Это прогрев дескриптора/цепочки; HTML, TLS и DOM по-прежнему обрабатывает Chromium. Прямого подключения или шлюза нет.

Ожидание ограничено180секундами, одновременных прогревов максимум16, записей кэша64, успешный результат действует60секунд. Таймеры/сокеты уничтожаются при ошибке, stop, circuit, identity и Kill Switch; запрос после ожидания повторно проверяет состояние Tor, offline, профиль и Kill Switch. Cookie/cache/localStorage не переносятся. Неправильные v3/локальные/не-Tor запросы не попадают в этот механизм. Подтверждение TCP не гарантирует доступность HTTP-сервиса или следующей цепочки.

Bootstrap больше не обрывается через фиксированные180секунд при продолжающемся прогрессе: действует180секунд без повышения прогресса и600секунд общего ожидания. Повторные предупреждения не продлевают срок. Пользователь может остановить соединение. Из control events сохраняются только bounded keywords TAG/REASON/COUNT/RECOMMENDATION; WARNING/HOST/HOSTADDR и произвольные строки журнала не экспортируются. Формат событий: [Tor control specification](https://spec.torproject.org/control-spec/replies.html). Потеря control channel блокирует Tor-профиль; timeout канала закрывает socket, чтобы поздний ответ не использовался следующей командой.

Проверка разработки0.5.2: собственный только что опубликованный v3 сервис открылся с первой попытки за113.073секунды (без HSFETCH и reload); весь real Tor matrix прошёл154секунды. Это пример холодного соединения, не SLA. Детерминированный Electron regression использует31секундную задержку SOCKS и настоящий DOM, чтобы проверить превышение Chromium-дедлайна. Реальные тесты используют собственный временный сервис, а не случайные onion; публикация сервиса и клиент в одном daemon — ограничение топологии. Smoke флаг --wait-descriptor только явно проверяет readiness своего fixture через HSFETCH и по умолчанию выключен. Сбои операторов, CAPTCHA и отсутствие сервиса не обходятся и не подменяются успешной страницей.

Кэш Tor после crash/stop теперь переиспользуется только внутри текущей сессии приложения: DataDirectory первого запуска хранит consensus/guard state, последующие torrc/control cookies отдельные; браузерный Tor-профиль всё равно новый. Tor.clear и штатный exit удаляют все run directories и кэш. Это сохраняет стабильный entry guard и не заставляет каждый restart заново скачивать все microdescriptors. [Почему guard стабилен](https://support.torproject.org/tor-browser/security/guard-relay/). Cookies/история/содержимое страниц не переносятся в этот кэш. Первый запуск после полной очистки остаётся холодным; доступность сети не гарантируется.
